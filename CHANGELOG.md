### Added

- **New `resource.response-empty` lint rule** (#255). A response typed to the base
  `Illuminate\Http\Resources\Json\JsonResource` (or an abstract subclass) the generator can't
  extract a shape from ships an empty `{data: {}}` envelope, but no rule flagged it:
  `resource.response-ambiguous` fires only for a collection with no item class, and
  `resource.fields-undeclared` deliberately skips the base/abstract class. The new ApiResources
  plugin rule (level 1) fills the gap — it fires exactly where `fields-undeclared` skips, gated on
  the same emptiness checks (no readable `toArray()` literal fields, no resolvable wrapped model),
  so a base/abstract resource that *does* carry an inferable shape isn't flagged. The three rules
  now partition every way a resource response ends up shapeless. Bagisto's ~100 `new JsonResource([…])`
  returns now surface a finding instead of silently documenting an empty payload. See
  [Linting](docs/linting.md).
- **Fractal transformer schemas are now inferred from the `transform()` literal** (#13). When a
  transformer's `transform()` is a single `return [...]` array literal (Tier-1 bounded scan, epic
  #5), its keys become response properties without any `#[TransformerField]`: `$model->field`
  values type themselves from the **typed `transform()` parameter**'s Eloquent metadata (Tier-0),
  `(int)`/`(float)`/`(string)`/`(bool)`/`(array)` casts type the key by the cast (an `(array)`
  cast documents an array of unconstrained items — `items: {}`), literal
  scalars/arrays type themselves, and anything else keeps its key as an unconstrained property
  with one summarising generation-log note per transformer listing the affected key paths,
  values inside nested literals included. Declared `#[TransformerField]` /
  `#[TransformerInclude]` attributes win per field; inferred extras compose after them in literal
  order. Dynamic bodies degrade to the attribute-declared shape (note when that leaves the schema
  empty), attribute-free `TransformerAbstract` subclasses with a readable literal now resolve as
  `$ref` targets, and `fractal.fields-undeclared` goes quiet when inference yields fields. On top
  of that, the InvoiceNinja-style base-controller convention binds transformers without any
  attribute: a top-level `return $this->itemResponse(…)` / `$this->listResponse(…)` plus a
  concrete `$entity_transformer` property **default** emits the single / collection
  `DataArraySerializer` envelope around the transformer's schema — a method that reassigns
  `$entity_transformer` (or has no usable default) degrades with a note, and `#[FractalResponse]`
  always wins. See [Plugins → Fractal](docs/plugins.md#fractal).
- **Constructor `$this->middleware(...)` now survives non-instantiable controllers** (#16). Laravel
  itself resolves controller middleware when routes are gathered — the static
  `HasMiddleware::middleware()` form without instantiation, the classic constructor form by
  instantiating the controller through the container, both honouring `only` / `except`. The gap was
  the controller the container *cannot* build at generation time (unbound constructor dependency, a
  constructor that throws outside a real request): `Route::gatherMiddleware()` threw, crashed the
  whole run, and poisoned the route's middleware cache so a retry silently returned `[]`. All
  middleware reads now flow through one crash-safe seam (`RouteMiddlewareGatherer`): on an
  instantiation failure it logs a notice and falls back to the route-declared middleware merged with
  a bounded static scan of the constructor body (Tier-1, first 10 top-level statements, epic #5) —
  literal `$this->middleware(...)` names with literal fluent `->only(...)` / `->except(...)` or
  options-array scoping, matched against the route's action method, deduplicated against
  route-declared names. Inherited (base-controller) constructors are read through their declaring
  class. Security schemes, per-operation `security`, the implicit 401/403/429 responses, multi-spec
  `match.middleware`, and `openapi:why` all see the same merged list; `#[Security]` /
  `#[PublicEndpoint]` keep winning. Dynamic names, non-literal scoping, and conditionally applied
  registrations are refused with a generation-log notice (documenting conditional auth as
  unconditional would overstate the contract). See
  [Auto-derivation → Controller middleware](docs/auto-derivation.md#controller-middleware).
- **`spatie/laravel-query-builder` fluent chains now document themselves** (#15). The QueryBuilder
  plugin reads the literal `QueryBuilder::for(...)->allowedFilters([...])->allowedSorts([...])
  ->allowedIncludes([...])` chain straight from the controller method body (Tier-1 bounded scan of
  the first 10 top-level statements, epic #5) and emits the matching `filter[…]` / `sort` /
  `include` query parameters — previously the plugin was attribute-gated and the most common form
  of the convention produced nothing. The chain must root at the **resolved**
  `Spatie\QueryBuilder\QueryBuilder` FQCN (a same-named impostor never matches); intermediate chain
  links (`->where()`, `->defaultSort()`, `->paginate()`, …) are walked through, since they cannot
  change which allow-lists the builder accepts. Allow-list elements resolve from string literals
  (class-constant strings included) and from Spatie's value-object static constructors
  (`AllowedFilter::exact/partial/scope/…`, `AllowedSort::field/…`,
  `AllowedInclude::relationship/…` — the first argument is always the public wire name; internal
  names and `->defaultSort(…)` are server-side detail and not modelled, and a bare
  `AllowedFilter::trashed()` defaults to Spatie's `trashed`). Both the array and the variadic form
  work, sort names shed their `-` direction prefix, and a chain assigned to a variable in one
  expression reads fine. Chain-derived filters get a `string` schema (`#[AllowedFilter]` is the
  hatch for typed filters); sorts/includes emit the same enum'd `sort` / `include` parameters as
  the attributes, so both sources converge on identical output. Precedence is **per kind**: any
  attribute of a kind present means that kind comes from attributes only, and a fully attributed
  action is never scanned. Degradation per the epic contract: a builder mutated across statements,
  a dynamic allow-list, or a chain inside a conditional yields no chain parameters with one
  generation-log notice pointing at the attributes; a non-literal element inside an otherwise
  literal allow-list is dropped and the rest kept. No variable tracking or cross-call dataflow
  (Tier 2 stays refused). The `examples/query-builder` flavor gains an attribute-free chain-only
  endpoint. See [Plugins → QueryBuilder](docs/plugins.md#querybuilder).
- **Concrete API Resources now resolve from the controller's return expression** (#108). When an
  action's signature names only a *base* resource type (`JsonResource`, a bare `ResourceCollection`,
  `AnonymousResourceCollection`) — previously an ambiguous endpoint with no response schema — the
  ApiResources plugin reads the method's return expression (Tier-1 bounded scan of the first 10
  statements, no dataflow): `X::collection(…)` / `X::make(…)` / `new X(…)` name the concrete
  resource (including the two-statement `$x = …; return $x;` form and `->additional(…)` chains);
  `->toResource(X::class)` / `->toResourceCollection(X::class)` take the literal class argument; a
  bare `$model->toResource()` on a Model-typed parameter resolves Laravel's own convention
  (`#[UseResource]`, then `guessResourceName()`); `new JsonResource($model)` documents the wrapped
  model's schema directly; and a `@return AnonymousResourceCollection<X>` docblock generic is
  honoured, winning over the body. The named class must be a *concrete* resource: a call on the base
  `JsonResource` itself or on an abstract subclass refuses (there is no field shape to document). A
  collection only claims the paginated `{data, links, meta}` envelope when its source visibly ends
  in a `paginate()`-family call — looking through the paginator-preserving chain links
  `withQueryString()` / `appends()` / `withPath()` / `fragment()` — any other collection source
  documents a plain `{data}` envelope, so pagination meta is never guessed. Conditional or otherwise
  unresolvable returns keep the previous behaviour plus one generation-log note per action,
  `#[ResponseResource]` always wins, and `resource.response-ambiguous` stops firing for
  body-resolved collections. The `examples/api-resources` flavor gains an annotation-free
  `BookingResource::collection()` index endpoint. See
  [Plugins → ApiResources](docs/plugins.md#resolving-the-resource-from-the-return-expression).
- **Framework-managed timestamp columns (`created_at` / `updated_at`) are now typed on Eloquent model schemas** (#250). Laravel's timestamps live in none of the metadata sources `EloquentModelToSchema` unions (`$casts`, `@property` tags, `$appends`, `$fillable` — the framework manages them via `$timestamps`, not `$casts`), so `propertyFor('created_at')` returned null and the columns were missing from direct-model schemas and unconstrained in every inferred Resource (the dominant noise term in the #247 review's per-resource degradation notices: all 24 inferred resources on clean Vito listed them). When the model reports `usesTimestamps()`, the columns named by `getCreatedAtColumn()` / `getUpdatedAtColumn()` (respecting `CREATED_AT`/`UPDATED_AT` renames; a `null` constant disables that side) now join the known-property union typed `string` / format `date-time`, nullable per runtime reality (unsaved models and `NULL` columns carry no value). The default sits **below** every explicit source — a `$casts` entry or `@property` tag for the same column still wins — and timestamp-only columns never enter `required`. Flows through direct model responses, Resource `$this->created_at` references, and relation `$ref`s alike; the `examples/vanilla` snapshot gains the two columns on `Flight`. See [Auto-derivation → Eloquent model response schemas](docs/auto-derivation.md#eloquent-model-response-schemas).
- **API Resource response schemas are now inferred from the `toArray()` array literal** — the fifth Tier-1 bounded body scan (epic #5) and, per the OSS survey (#106), the single highest-value one: 72 operations across the surveyed apps are typed to concrete Resources whose `toArray()` is one static `return [...]` literal, previously documented as nothing. The bounded case is exactly that shape — `toArray()` overridden outside the framework, exactly one top-level `return` statement returning an array literal (shared primitive: the new `Support\MethodBody\SingleReturnArrayLiteralFinder`, which the Fractal `transform()` reader (#13) will reuse). The literal's string keys become response properties; each value resolves best-effort, refusing per value: `$this->field` / `$this->resource->field` resolve against the **wrapped model's** metadata via the #18 reader — `EloquentModelToSchema` gains a memoised per-property `propertyFor()` lookup (casts, `@property`/`@property-read` tags, typed `$appends` accessors) without `$hidden`/`$visible` filtering, since a resource naming a key has already decided it is output — with the model discovered from the resource docblock by the new `WrappedModelLocator` (`@mixin` first, then a generic `@extends Base<Model>`); literal scalars and arrays type themselves through the shared literal mapping (extracted from #14's resolver into `Support\MethodBody\SchemaDefinitionFromLiteral`); nested `new OtherResource(...)` / `OtherResource::make(...)` become a `$ref` to that resource's schema and `OtherResource::collection(...)` an array of `$ref`s, self-referencing resources terminating through the component registry's existing cycle guard; the canonical conditional idioms `$this->when(...)` / `$this->whenLoaded(...)` mark the key **optional** (kept in `properties`, omitted from `required` — the condition is never analysed, the same rule as the abort scan) and resolve their inner value, a bare `whenLoaded('relation')` resolving the relation against the model, `$this->whenCounted(...)` documenting an optional `integer` and any other `when*` wrapper an unconstrained optional property; `$this->merge([...])` / `$this->mergeWhen(..., [...])` inline their literal payload's keys at the top level (optional for `mergeWhen`), a non-literal payload being skipped with a generation-log note. Any other value (a method call, a ternary, a field the model does not know) keeps its key as an **unconstrained property** — dropping a response property would be silently wrong, the #14 precedent — with one summarising note per resource listing the affected keys. `#[ResourceField]` wins **per field**; inferred fields it does not cover compose alongside in literal order. This also delivers the folded #98 **passthrough base case**: a resource with no `toArray()` override, no attributes, and a resolvable wrapped model documents as the *model's* component directly (no empty `*Resource` component is created); a dynamic, unreadable `toArray()` takes the same model fallback with a note, or stays at today's attribute-driven behaviour. Envelopes (`{data}` / `{data, links, meta}`) are untouched — only the item schema is filled — and `resource.fields-undeclared` now stays quiet whenever inference or the model fallback produces a non-empty schema. See [Plugins → ApiResources](docs/plugins.md#apiresources) and the reworked [`examples/api-resources/`](examples/api-resources/). (#12)
- **Query parameters are now inferred from `$request->*()` accessor reads in the controller method body** — the fourth Tier-1 bounded body scan (epic #5), reusing the shared `Support\MethodBody` primitives. The first 10 top-level statements are scanned for five accessor shapes on the request — `query('sort')` / `input('q')` → `string`, `string('name')` → `string`, `integer('page')` → `integer`, `boolean('active')` → `boolean` — and each read becomes a query parameter. The receiver must be the method's `Illuminate\Http\Request`(-subclass)-typed parameter or a zero-argument `request()` helper call; the name is the first string-literal argument (positional or named `key:`), with dotted keys documented in wire notation (`filter.name` → `filter[name]`); a literal, type-matching default (`integer('per_page', 25)`) becomes the schema `default`. Unlike the body/response scans, reads inside conditional contexts (an `if` branch, a `->when(...)` closure) still match — a read claims nothing beyond "this parameter is consumed". `query()` matches on every verb; the other four read the merged body+query input and match only on GET/HEAD routes. A closure or arrow function that re-declares the receiver variable name shadows it — reads inside that subtree are on a different request and never match (`use` captures and arrow-function implicit captures still do). A non-literal name degrades that read with a generation-log note, gated by the same verb discipline as the read itself.
- **On GET/HEAD routes, inline `validate()` keys now become query parameters** instead of a request body — closing the hand-off #9 deliberately left open. Recovered rules map to parameters with rule-derived schemas (type, format, constraints), `required` from the rules, and trailing-comment descriptions; nested keys flatten to the query-string wire format (`filter.name` → `filter[name]`, scalar `ids.*` → a repeatable `ids[]` with an array schema), while arrays of objects and the bare `*` rule are dropped with a generation-log note. Precedence is layered per name: an explicit `#[QueryParam]` wins entirely, `validate()` rules beat an accessor read of the same name, a typed accessor beats an untyped one, and parameters from different sources with different names compose. Inline `validate()` on a DELETE route stays undocumented by design — the fields may legitimately live in either the body or the query string — but now leaves a generation-log note pointing at `#[QueryParam]` / `#[RequestBody]` instead of vanishing silently.
- The primary response is now inferred from a **literal `response()->json([...])` call in the controller method body** — the third Tier-1 bounded body scan (epic #5), reusing the shared `Support\MethodBody` primitive from #9/#10. The first 10 top-level statements are scanned *excluding* conditional contexts (a `response()->json()` that only runs conditionally is not the canonical success response — the same reasoning as the inline-validation scan, opposite of the abort scan); only the zero-argument `response()` helper followed by `->json(...)` matches, with the same guess-resistant name resolution as the abort scan, and a *returned* `json()` beats one only assigned to a variable (among returned matches, the first wins). A literal array body becomes the response schema: nested literal arrays recurse into nested object schemas, literal scalars type their properties, a literal list becomes an array schema with items derived from its first element (explicit sequential integer keys count as a list, exactly as `json_encode` treats them), and a dynamic *value* under a literal key keeps the property with an unconstrained schema — dropping a response property would be silently wrong for spec consumers (the opposite trade-off from the request side, where a dropped field merely under-documents input). The `data` and `status` arguments resolve **by position or by name** (`response()->json(data: [...], status: 201)` — named-argument calls are a live corpus idiom, #234); a literal or class-constant `status` becomes the response status (`201` → `Created`), absent → `200`. A status the author wrote in the call now takes precedence over the resource-action convention (#25): a `store` returning `response()->json([...], 200)` documents `200`, not the convention's `201`, and an `index` returning `..., 201` keeps `201` rather than being relabelled `200` (#240). An *absent* status still defaults to `200` and stays subject to the convention, so a conventional `store` whose `json()` carries no status is still promoted to `201`. **Only a 2xx literal status may claim the primary response**: a straight-line non-2xx literal — the pervasive guarded-success + terminal-error-fallback idiom, `return response()->json(['message' => 'Unauthorized'], 403)` after a conditional success — degrades with a note instead of evicting the operation's success response (routing those literals into the error-response machinery, like #10's aborts, is #238), and a literal `204` documents as `204 No Content` without a body schema — the runtime strips the body. Degradation per the epic contract: a dynamic key or spread entry, a non-literal first argument (`$data` variables, model expressions, `compact()`), a non-literal status — the body must not be documented under a guessed status — or a chained call that can change the response's status or body (`->setStatusCode(201)`, `->setData(...)`; header/cookie chains stay matched, reading status-mutating chains is #236) skips the call with a generation-log note naming the action (`#[Response]` is the escape hatch); a method with no matching call, or a body with no shape (`json()` / `json([])`), stays silent. A schema-bearing return type (Model, Data, Resource, paginator) always wins via the resolver-chain order plus a return-type guard, an explicit `#[Response]` (2xx) attribute keeps overriding the inferred result, and an action carrying a primary-response authoring attribute — `#[ResponseResource]`, `#[FractalResponse]`, anything implementing the new `Contracts\Attributes\PrimaryResponseAuthoringAttribute` marker — is never scanned: the resolver consuming the attribute may sit later in the chain, and explicit authoring always wins. The `response()->json($model)` path from the issue spec is deferred until a model expression is resolvable without dataflow. Also extracts `OperationBuilder`'s array-definition → `OA\Schema` conversion into the shared `Support\Generator\SchemaFromArrayDefinition`, now used by both the `#[Response(schema: [...])]` path and this resolver. See [Auto-derivation → Inline JSON responses](docs/auto-derivation.md#inline-json-responses). (#14)
- The body-scan literal evaluator now resolves **class constants** on loadable classes, so `abort(Response::HTTP_FORBIDDEN, '…')` documents a 403 like its plain-integer twin — the dominant abort idiom in some apps (Koel writes all 46 of its abort statuses this way) previously skipped with a generation-log note. The class name must be statically known (imports and aliases are fine — the scanner's NameResolver pass has already resolved them) and the constant's value must itself be a scalar or array: enum cases are objects and stay non-literal, as do unresolved `self::`/`static::` references and dynamic `$class::CONST` / `Class::{$name}` fetches, which keep the existing graceful skip. Benefits every body-scan consumer uniformly — abort statuses (#10) and inline-validation rules referencing rule-set constants (#9) alike. Tier-0 trust on a Tier-1 scan: `class_exists` + `constant()` (an undefined constant's `Error` is caught and degrades to the skip), plain reflection, no dataflow. (#227)
- Error responses are now inferred from **`abort()` / `abort_if()` / `abort_unless()` calls in the controller method body** — the second Tier-1 bounded body scan (epic #5), reusing the shared `Support\MethodBody` scan primitive from #9. The first 10 top-level statements are scanned *including* conditional contexts (an `abort(403)` inside an `if` guard is exactly the outcome worth documenting; `StatementNodeFinder` gains a `findAll()` sibling to collect every match). A literal integer status in 400–599 becomes a response on the operation; a literal string message becomes its description (and stays inlined on that operation rather than being hoisted into the shared per-status response component — `ErrorDescriptor` gains a `shareableDescription` flag for this), otherwise the standard reason phrase is used and the response shares the named component as before. The condition argument of `abort_if`/`abort_unless` is never analysed, a non-literal status skips the call with a generation-log note naming the action, and a literal non-error status (`abort(302)`) is silently out of scope. The descriptors carry the exception `abort()` actually throws (`NotFoundHttpException` for 404, `HttpException` otherwise), so error-envelope resolvers treat them like every other contributor's. Registered after the `@throws` contributor and before the convention-derived ones; an explicit `#[Response]` for the same status still wins unconditionally. No variable tracking or cross-call dataflow (Tier 2 stays refused). See [Auto-derivation](docs/auto-derivation.md). (#10)
- Request bodies are now recovered from **validation rules declared inside the controller method** — the first Tier-1 bounded body scan (epic #5). A new shared scan primitive (`Support\MethodBody\MethodBodyScanner` + `AstLiteralEvaluator`, built on `nikic/php-parser` with a per-file AST cache) reads the first 10 top-level statements of an action and matches exactly four call shapes: `$request->validate([...])`, `$this->validate($request, [...])`, `Validator::make($request->all(), [...])`, and `Request::validate([...])`. The rules array literal flows through the same `ValidationRulesToSchema` mapping as a `FormRequest`'s `rules()` (constraints, `required`, nested keys, file rules → `multipart/form-data`), and a trailing `//` comment on a rule entry becomes the field's description. The rules argument may also reference a controller-declared `$rules` property or zero-argument `rules()` method, optionally subscripted with a literal key (`$this->rules()['create']` — the BookStack idiom). The resolver runs after the FormRequest resolver (Tier-0 miss only) and fires for POST/PUT/PATCH only — on GET no body is inferred; routing the recovered keys into query parameters is planned (#11). A matched call also documents the **422 validation error response** — the same `ValidationFailed` component a `FormRequest` parameter produces, emitted even when the rules themselves cannot be read (the call throws on failure either way). Dynamically-built rules are never guessed at: the operation keeps its empty body and a generation-log note names the action; `#[RequestBody]` / `#[RequestField]` remain the escape hatch and always win. No variable tracking or cross-call dataflow (Tier 2 stays refused). See [Request bodies → Inline validation in the controller](docs/request-bodies.md#inline-validation-in-the-controller). (#9)
- **Array-shape PHPDoc** (`array{foo: string, bar: int}`) is now resolved into an object schema instead of being dropped to a bare, untyped `array`. A new general `Support\Types\TypeNodeToSchema` resolver — the `TypeNode`-keyed companion to the existing `JsonSchemaFromType` (which is keyed on resolved symfony types) — handles the structural shapes that symfony/type-info cannot represent: a sealed shape → `type: object` with `properties` (each item key → a property, its value resolved recursively); an optional key (`array{name?: string}`) → omitted from `required`; a nested `array{…}` → a nested object; the list forms `list<array{…}>` / `array{…}[]` (and scalar lists like `string[]`) → `type: array` with `items`; and a string-keyed map `array<string, T>` → `additionalProperties: T`. Leaf class identifiers are delegated to a consumer-supplied strategy, so a Model leaf still becomes a `$ref` and any other class still goes through `JsonSchemaFromType`. Wired into Eloquent model `@property` resolution (`EloquentModelToSchema`), so an `@property array{…}` on a model becomes a fully-typed object schema; the resolver is reusable by the controller-return Tier-1 work landing separately. Pure Tier 0 — reflection/PHPDoc only, no method-body parsing. See [Auto-derivation → Property sources](docs/auto-derivation.md#property-sources-and-precedence). (#127)
- New **`lcov`** output format for `openapi:lint --format=lcov[:target]`. Emits an [LCOV](https://github.com/linux-test-project/lcov) tracefile (the same line-keyed coverage data as `cobertura`, in the format consumed by `genhtml`, VS Code coverage gutters, and GitLab / Bitbucket integrations). See [Linting → Output targets](docs/linting.md#output-targets). (#268)
- The served docs playground can now render with **Swagger UI** as an alternative to the default Scalar reference. Set `openapi.routes.playground.renderer` to `'swagger-ui'` (default `'scalar'`) and the `/api/docs` route serves a Swagger UI shell instead — its layout, "Try it out" affordances, and OAuth2 flow being what teams migrating from `darkaonline/l5-swagger` already know. Both shells are loaded from a CDN and point at the same per-spec YAML endpoint (resolved through the same `SpecRegistry` plumbing, so multi-spec works unchanged), so the switch is config-only with no asset-publishing step; an unrecognised renderer value falls back to Scalar. Not an inference concern — a pure serving-layer choice. See [Configuration → Routes](docs/config.md#routes). (#119)
- A backed enum referenced anywhere in the document now emits a **single reusable component** and is `$ref`'d at every site, instead of being inlined per context. A `BackedEnum` used as an Eloquent `$casts` entry, a Spatie `Data` property, a typed path/query parameter, or a full-set `Rule::enum(Status::class)` validation rule resolves to one `#/components/schemas/{Enum}` definition (its `type` from the backing kind — `string`/`integer` — and the `enum` case list, plus any per-case PHPDoc description) that all references point at. The promotion is centralized in `JsonSchemaFromType` — its `BackedEnumType` branch registers the component on `ComponentSchemaRegistry::buildOnce()` keyed by enum class-string and returns a `$ref` — so every type-derived site (cast, Data property, parameter) inherits dedup uniformly; a nullable enum wraps as `oneOf: [{$ref}, {type: null}]` per OAS 3.1. The validation-rule path participates only when the rule constrains the field to the enum's **full** case set: a `->only(...)` / `->except(...)` subset, or a unit (non-backed) enum, keeps its inline value list, since a subset is not the canonical component. Inline sibling keywords that a `$ref` cannot carry (a per-field `example`) are dropped, matching the library's existing `$ref` behavior. Tier 0 — pure reflection on `::cases()`. (#35)

- `ValidationRulesToSchema` now maps four validation rules it previously dropped at its silent-ignore arm (#83): `multiple_of:N` → `multipleOf` (integer args stay int, decimal args become float — needed a new `multipleOf` slot on `FieldDescriptor`, wired through to the `OA\Schema` output), `active_url` → `format: uri` (consistent with `url`), `mac_address` → a colon/hyphen six-octet `pattern`, and `hex_color` → an optional-`#` six-digit hex `pattern`. `lowercase`/`uppercase` (only a lossy ASCII pattern that wrongly accepts multibyte uppercase) and `current_password` (a server-side auth check with no schema shape) stay intentionally unmapped. See [Request bodies → Validation rules → schema constraints](docs/request-bodies.md#validation-rules--schema-constraints).
- Sanctum security-scheme auto-derivation (#32): when any discovered route carries the `auth:sanctum` middleware, the generator now registers a `sanctum` http/bearer security scheme and emits the per-operation `security` requirement for those routes — previously a Sanctum-protected API produced zero schemes and empty `security`, silently mislabelling protected routes. Detection keys off the `auth:sanctum` middleware token rather than `class_exists(Sanctum::class)`, because Sanctum ships by default in fresh Laravel apps and is not always used for API auth; the token is the only signal that it is. The scheme joins the auto-derived defaults (after Passport's pair when both are present), config still wins on name collision, and the `#[Security]` / `#[PublicEndpoint]` override hatch is unchanged. Sanctum token *abilities* (`abilities:` / `ability:` middleware → scopes) remain unmapped — tracked as #90. Surfaced across six OSS-survey apps (Pelican, Koel, Vito, AdvisingApp, Speedtest Tracker, AureusERP).

### Changed

- Extracted the spec route-URI convention into a single `Support\Spec\SpecRouteConfig` helper
  (`@internal`), removing the duplicated `route_uri` / `playground_uri` resolution that previously
  lived inline in both `SpecRegistry::buildSpec()` and the service provider's route mounting. The
  two copies are now one source of truth, so the served route path and the generated spec path can
  no longer drift. Extracting the two copies surfaced a latent divergence on a `null` URI override:
  `SpecRegistry` already treated `null` (like `false`) as opting the spec out of HTTP serving, but
  the service provider's `?? default` fall-through still mounted the route. Both now opt out on
  `null`, matching the documented config convention (`false`/`null` = do not mount). The `false`
  case and all string overrides are unchanged. (#48)
- PHP 8.4 modernization pass across `src/`. Every method that implements an interface or overrides
  a parent now carries `#[Override]` (118 added, bringing the codebase to full coverage); `foreach`
  search/existence/universal loops over plain arrays were replaced with `array_find` / `array_any`
  / `array_all` where it reads more clearly; and pure boolean accessors became `get`-hook virtual
  properties (read as `$response->isSuccess`, not `$response->isSuccess()`), matching the existing
  `DocComment::$empty` convention: `ResponseNode` (`isSuccess` / `isError` / `isRedirect` /
  `isDefault`), `RequestBodyNode` (`isMultipart` / `isJson`), `LintOptions::isScoped`,
  `FixResult::hasChanges`, `OverrideMatcher::hasOverrides`, and `ResourceTarget::isAmbiguous`.
  Because hooked properties may not be readonly, the four value objects that were `final readonly
  class` move the `readonly` modifier from the class onto each property — immutability is
  unchanged. No change to generated documents or lint output.
- The `Formatter::render()` interface signature is collapsed from five positional parameters (`$findings`, `$level`, `$exitCode`, `$output`, `$coverage`) into `render(LintResult $result, OutputInterface $output): void`. Each formatter reads only the fields it needs from the result object. Custom `Formatter` implementations must update their signature. (#267)
- The OpenAPI stage pipeline order is now expressed as a single ordered sequence in one place — `BaselineRegistration::assemble()` — instead of being split across `BaselineRegistration` (baseline stages first), the plugin loop, and two terminal steps `SpecPipeline` held as injected fields. `assemble()` reads top-to-bottom: pre-plugin baseline stages (`RootStage` → `PathsStage` → `ErrorResponseInferenceStage`) → plugin stages → post-plugin stages (`ComponentsStage` → `SecurityStage` → `OverridesStage` → `TransformersStage`), then the lint rules and error-envelope resolver, then `seal()`. It stays plugin-agnostic (it lives in `Support\`): the `OpenApiServiceProvider` factory closure owns only the Laravel/config glue and passes the plugin list, config rules, and resolved envelope class in as class-strings. `SpecPipeline` becomes a pure executor that just loops the registered stages. The `ComponentsStage` flush consequently runs **after** the plugin loop, so a late stage that contributes schemas (the SwaggerPhp harvester, and any future one) registers them on `ComponentSchemaRegistry` like every other contributor — the harvester's bespoke direct-write to `$document->components` (with its own dedup, no schema-transformer dispatch) is removed in favour of `registerNamed()`. The terminal-stage "runs last" guarantee is now positional (it holds because all registration funnels through `assemble()` before the terminal `addStage` calls) rather than structural; `OpenApiRegistry::seal()` is called at the end of assembly to enforce that funnel, rejecting out-of-band `addX()` on the built registry with an (unchecked) `RegistrySealedException`. Internal wiring only — no change to the generated document for any bundled configuration. (#190)
- The auto-derived operation **tag** now comes from the controller's short class name — the `Controller` suffix stripped and the remainder pluralised (`PostController` → `Posts`) — instead of the last meaningful segment of the controller's namespace. This groups endpoints per-resource out of the box: an app whose controllers all live in `App\Http\Controllers` (the Laravel default) previously collapsed every operation under a single `Controllers`-skipped fallback (`General`); each now gets its own `Posts` / `Users` / `Invoices` group. Closure/controllerless routes fall back to the StudlyCased last segment of the route-group prefix (`prefix('webhooks')` → `Webhooks`), then to `General`. The `#[Tag]` (additive) and `#[Operation(tags:, replace: true)]` (replace) escape hatches are unchanged and still operate against this derived baseline; derivation logic moved into a dedicated `Support\Generator\TagDeriver`. The example snapshots are regenerated accordingly — controllers carrying an explicit `#[Tag('Flights')]` now dedupe against the matching derived tag rather than stacking a redundant flavor tag. See [Auto-derivation → Tag](docs/auto-derivation.md). (#37)
- Resolver fault isolation is now centralized in a single `Support\Registry\ResolverFaultBoundary`, applied uniformly at every resolver seam — primary-response, request-schema, query-parameter, and ref-schema (`OperationBuilder` and `RequestBodyExtractor`), including third-party plugin resolvers. Previously each resolver self-isolated inconsistently (some `catch (Throwable)`, some only `catch (ReflectionException)`, others not at all), so whether one malformed route degraded gracefully or aborted the whole `openapi:generate` run depended on which resolver happened to handle it. The boundary catches `Exception` only: a malformed route logs a warning (with route + resolver context) and is skipped while the rest of the document still generates, but `Error`/`TypeError` — programming bugs in resolver code — now propagate as stack traces instead of being swallowed into a silently missing schema. The five primary-response resolvers' redundant route-level `catch` blocks were removed; `SchemaFromFormRequest` and `SchemaFromDataClass` keep their fine-grained degrade-with-fallback catches (which still emit a degraded finding / partial schema) over `Throwable`, since they invoke arbitrary host-app code (`rules()` / `getValidationRules()`) that routinely raises `Error`/`TypeError` at spec time. No behaviour change for well-formed routes. (#100)
- Relocated the shared `ValidationRulesToSchema` (Laravel validation-rule → JSON-Schema mapper) and `FakerExampleSynthesiser` from `Plugins\Core\Support\` to `Support\Extraction\`. Both are plugin-agnostic and used by Core and the SpatieData plugin alike; living under `Support\` lets the convention plugins reach them without importing the Core plugin, which the new plugin-isolation arch test now forbids. Behaviour is unchanged.
- Lint rules `tag.duplicate` and `queryparam.duplicate` now detect duplicates by reading the `#[Tag]` / `#[QueryParam]` attributes on the controller method via reflection, rather than scanning the generated operation. The generator deduplicates both upstream (tags via `array_unique`, query parameters keyed by name), so a repeated attribute never reached the old spec-level check and the rules could not fire from real code — which also meant their `--fix` removers could never run. Severities were corrected to match impact: `tag.duplicate` 0 → 3 (a redundant tag changes nothing in the valid output — pure source hygiene, alongside `field.no-effect`), `queryparam.duplicate` 0 → 1 (the last-wins merge silently drops the earlier declaration's details). Consequence: `tag.duplicate` now only runs at `--level=3`/`max`; `queryparam.duplicate` still runs at the default level. The guarantee that duplicate parameter `(name, in)` never reach the document is unchanged, still enforced by the level-0 `parameter.duplicate-name`. Surfaced by Phase 1 dogfooding (#78).
- Widened `zircote/swagger-php` support to `^5.8 || ^6.1.2`, so apps pinning swagger-php 5.x
  (e.g. those that self-generate OpenAPI from `#[OA\*]` attributes) can install the package.

The component is used only for type→schema mapping and the APIs we rely on are stable across the 7.3 and 8.x lines; pinning `^8` needlessly forced a Symfony 8 component into otherwise Symfony-7 Laravel 12 installs. Verified against both the 7.3 floor and the 8.x line (full suite + PHPStan L8). Surfaced by OSS-survey dogfooding (`docs/internal/dogfooding/2026-05-31-pelican-spatie-data-pre-4.23-blocks-install.md`).
- Default `config('openapi.filters')` now includes `SkipSelfRoutes` as the first entry. A stock install no longer documents the library's own `/api/openapi.yaml` and `/api/docs` endpoints in the generated spec. Remove the entry from your published config to opt back in.
- CI matrix pins `orchestra/testbench` per Laravel cell (`^10.0` for `laravel: 12.*`, `^11.0` for `laravel: 13.*`) and asserts the resolved `laravel/framework` major matches the matrix variable after `composer update`. Previously the `12.*` cell silently floated to Laravel 13 via testbench 11, letting a Laravel-13-only API ship and break the package on the entire L12 range. `tests/TestCase::defineEnvironment()` also forces `filesystems.disks.local.serve` to false so the testbench-10 default (which registers two extra `storage/{path}` routes that aren't in the testbench-11 baseline) doesn't drift snapshots between cells. Surfaced by OSS-survey dogfooding (`docs/internal/dogfooding/2026-05-30-survey-ci-laravel12-cell-illusory.md`).

### Fixed
- `ResourceConventionResolver` now gates on the pinned emitted verb (`$descriptor->httpMethod`) rather than the full verb list on the route object. On a multi-verb route such as `Route::match(['GET', 'POST'], …, 'store')`, `array_intersect` was non-empty for both twins, so the GET operation wrongly received the `store` convention (status 201 and a "Create …" summary). The fix matches the pattern used by the other verb-conditional resolvers: extract `$descriptor->httpMethod->forDisplay()` and require an exact match in the convention's verb list. Single-verb routes are unaffected.
- `#[ResponseField(conditional: true)]` on a Spatie Data class property now removes that field from `required[]` as documented, matching the semantics already honored by the ApiResources and Fractal backends. Previously, the SpatieData backend applied the `FieldAttribute` descriptor (Pass 3 of `SchemaFromDataClass`) but never consulted the `conditional` flag, so the field stayed in `required` despite the attribute.
- Validation constraint keywords (`minItems`, `maxItems`, `uniqueItems`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `multipleOf`, `pattern`, `format`, `enum`) are now migrated into the inner `oneOf` branch when a `nullable` array or object field is restructured for OAS 3.1 nullability. This is fixed in **both** restructuring sites: `FieldDescriptor::applyTo()` (the validation-rules path) and `NullableSchema::applyTo()` (the in-place helper reached via `SchemaDescriptor::toSchema()`/`applyTo()` — e.g. a `#[ResponseField(type: 'array', nullable: true, minItems: 1, maxItems: 10)]` and the other field attributes). Both previously wrote these keywords onto `$target` before the nullable block moved `type`/`items`/`properties` into a `oneOf: [{type: array, …}, {type: 'null'}]` inner schema, stranding the constraints on the typeless outer `oneOf` schema where per-branch JSON Schema validators ignore them. Scalar fields (`string`, `integer`, `number`, `boolean`) use the `type`-array path and were unaffected. `description` and `example` remain on the outer schema — they are field-level metadata, not per-branch validators. (#279)
- Single-argument `array<T>`, `non-empty-list<T>`, and `non-empty-array<T>` now resolve to `type: array` in the cast path, matching what the pure-tag path already produced (#284). `TypeNodeResolver::listValueType()` — used by `EloquentModelToSchema::jsonCastDefinition()` — only recognised `list<T>` and `array<int, T>` as lists, so `array<string>` on a cast column silently fell back to `type: object` while the same annotation on an uncast column produced `type: array` via `TypeNodeToSchema::fromGeneric`. The two paths now agree for all single-argument array/list generics.
- `encrypted:array`, `encrypted:collection`, `encrypted:json`, and `encrypted:object` casts now map to the same schema as their non-encrypted counterparts instead of collapsing to `type: string` (#283). `EloquentModelToSchema::castToProperty()` reduced every cast to its head keyword via `strtok($cast, ':')`, so all parameterised `encrypted:*` forms became `encrypted` and hit the string arm. The fix detects the `encrypted:<inner>` form before the keyword dispatch, strips the prefix, and recurses with `<inner>` — so `encrypted:array`/`json`/`collection` inherit the `@property`-tag list disambiguation, and `encrypted:object` resolves to `type: object`. Bare `encrypted` (no parameter, a string at runtime) is unchanged.
- `openapi:lint --list` now honors file targets: `--format=json:catalog.json` writes the rule catalog to the file instead of silently falling back to stdout. Stdout is still used when no file path is given. (#298)
- `RuleRegistry::effectiveLevelFor()` now floors negative `severity_overrides` values to `0` via `max(0, …)`. A negative override (e.g. `-1`) previously propagated unchanged, causing a rule to always match every `forLevel()` threshold. (#296)
- `#[Deprecated]` no longer declares `Attribute::TARGET_CLASS_CONSTANT` as a valid target. No code in the package reads `#[Deprecated]` off class constants (only methods, functions, properties, and promoted constructor parameters are consumed), so placing the attribute on a constant was a silent no-op. Removing the flag lets PHP reject the misplacement at attribute-resolution time rather than silently ignoring it. (#297)
- `OverridesStage` now normalises a `tags` override to a sequential `list<string>` (via `array_values`) before assigning it to `OA\Operation->tags`, matching the form the rest of the pipeline produces and satisfying swagger-php's `[string]` type validation (`array_is_list` check) on both 5.8 and 6.x.
- `@return AnonymousResourceCollection<X>` on a non-paginating action no longer emits the `{data, links, meta}` envelope. `targetFromReturnTag()` defaulted `paginated: true` when it resolved the item class from the docblock generic — so any annotated collection claimed pagination regardless of what the body actually returned. The return-tag path now derives pagination from the method body via the same `endsInPaginatingCall()` evidence the body-scan path uses: `paginated: true` only when the body's single unconditional `X::collection($source)` call's argument visibly ends in a `paginate()`-family call (looking through paginator-preserving links). When no body evidence is available (no parseable return expression, abstract method, no source file), the safe default is `{data}` — the common case — rather than silently claiming a pagination envelope that the runtime response does not carry.
- `OverridesStage` now applies `openapi.overrides` to webhook operations. Previously the stage iterated only `$document->paths`, so any override targeting a webhook operation was silently dropped. The stage now also iterates `$document->webhooks`, guarded against `webhooks` being `Generator::UNDEFINED` when no `#[Webhook]` routes are present. A webhook operation is matched by its **webhook name** (the `#[Webhook(name: …)]` value that appears under `webhooks` in the spec) — exactly or via glob — not by its route URI; the exact route-name key still applies. The companion `overrides.unused` lint rule (`OverridesUnused`) is aligned to the same rule: a key matching a webhook name is recognised as used (it was previously flagged as unused, since the rule only checked route names and route URIs), and a key matching only a webhook's route URI is no longer reported as used. Both sides derive the webhook key through the shared `OverrideMatcher::webhookKeyFor()`, so the stage and the rule can't drift. (#286)
- A new PHPStan rule (`openapi.requestField.nameRequiredOnMethod`) flags `#[RequestField]` on a method or function that omits `name:`. The name cannot be derived from a method target — the runtime silently drops the field in that case. Properties and promoted constructor parameters are not affected: the name is legitimately derived from those targets. The rule accepts both named (`name: 'foo'`) and positional (`'foo'`) first-argument forms. See [Linting → Static checks](docs/linting.md#static-checks-phpstan).
- Class-level `#[IgnoreLint]` on a controller now suppresses findings for that class only, not for every class in the same file. `SuppressionDirective` for `ClassScope` previously fell back to file-path matching when a finding had no `CONTEXT_SOURCE_CLASS` context — so a single-file controller with two classes had its suppression bleed to the other class. The fix has two parts: (1) `ClassScope` now requires `CONTEXT_SOURCE_CLASS` to match (the file-path fallback is removed); (2) `SpecTreeWalker` stamps `CONTEXT_SOURCE_CLASS` (the controller FQCN from `ActionDescriptor::$controller`) on **every** finding emitted under an operation — operation-level findings plus the `response.*`/`parameter.*`/`header.*`/`link.*`/example findings on its sub-nodes — via a `stampSourceClass()` pass, so class-scope directives on controllers can match those findings structurally. The stamp is a **fallback**: findings that already carry a more-specific source class (e.g. request-body or response fields attributed to their component schema) keep theirs, so property-scope suppression on payload classes is unaffected.
- `SchemaDescriptor::toSchema()` no longer defaults an untyped descriptor to `type: string` (#291). It seeded every schema with a hardcoded `type: 'string'` before spreading `toOpenApi()`, so a descriptor with no explicit type — e.g. `#[QueryParam(name: 'per_page', nullable: true)]` — was wrongly constrained to a string (`type: ['string', 'null']` once nullable widening applied). An untyped descriptor now produces an open schema (no `type`); an explicit type still emits that type, and an explicit nullable type still widens to the OAS 3.1 `[type, 'null']` shape. The two `toSchema()` callers were audited: `#[QueryParam]` and `#[AllowedFilter]` (QueryBuilder plugin). Both bundled fixtures that intended a string already set `type: 'string'` explicitly; an untyped `#[AllowedFilter]` is already flagged by the `querybuilder.filter-type-missing` lint rule rather than silently defaulting. Path/header parameters are unaffected — `UriParametersExtractor` builds its schema from the parameter type, not via `toSchema()`.
- The Tier-1 body scanner now logs when a controller file fails to parse instead of degrading silently. `MethodBodyScanner` caught the parse `Throwable` and cached an empty result, so a file with a syntax/encoding issue silently produced no Tier-1 inference for any of its methods with no diagnostic — matching the "degrade gracefully **and log**" contract the other extractors follow. It now logs at `notice` (file path + exception) via an injected `LoggerInterface` (a `NullLogger` default keeps the many direct constructions working; the container injects the real logger on the generation/lint path). Degradation behaviour is otherwise unchanged.
- The `deprecated.attribute` lint rule (`DeprecatedAttribute`) now implements `Resettable`, so its per-attribute `ReflectionClass` cache is cleared before each walk instead of accumulating across runs in a long-lived process (Octane, test suites). Matches the reset protocol the other stateful rules already follow.
- The Tier-1 literal mapper no longer imposes the first element's shape on a list of differently-shaped objects. `SchemaDefinitionFromLiteral::listDefinition()` compared only the top-level `type`, so a `response()->json([...])` / `toArray()` / `transform()` list like `[['status' => 'active', 'expires_at' => '…'], ['status' => 'inactive']]` (both `type: object`) documented `expires_at` as an always-present property when it appears on only one element. Object elements now must also agree on their property shape; a list of objects with differing keys degrades to unconstrained `items: {}`, matching how the mapper already handles type-disagreeing lists. Homogeneous object lists are unchanged.
- A throwing `LintFindingEmitted` listener no longer aborts the whole lint run. `EventDispatchingFindingsCollector::emit()` dispatched the per-finding event un-isolated, so a buggy host-app listener (e.g. a notification hook that fails) propagated out of the collector and discarded every finding collected so far for that spec. The dispatch is now wrapped: a listener throwable is logged (`warning`) and the finding is still handed to the inner collector. Runs with no registered listener are unchanged (the `hasListeners()` gate still short-circuits).
- `NullableSchema::applyTo()` (the in-place nullable variant) now guards the `$ref` case and migrates an object's structural keywords, matching `wrap()` and `FieldDescriptor::applyTo()`. Previously, applied to a `$ref`-bearing schema it wrote `type: ['null']` directly onto the reference — an impossible constraint in OAS 3.1, where `$ref` is no longer exclusive — and for a `type: object` it moved only `items` into the `oneOf` inner branch, stranding `properties` / `required` / `additionalProperties` on the now-typeless outer schema. `SchemaDescriptor::toSchema()`/`applyTo()` reaches the structured branch when a field attribute declares a nullable `array`/`object` type (see the `#279` entry above for the constraint-keyword half of the same fix). so `operation.security-missing` and `publicendpoint.contradicts-middleware` no longer miss controller-applied auth middleware (#260). Since #258 the generator reads middleware through the crash-safe `RouteMiddlewareGatherer` (constructor `$this->middleware(...)`, the static `HasMiddleware` form, plus the static-scan fallback), but `OperationNode::hasAuthMiddleware()` and `PublicEndpointContradictsMw::findConflictingMiddleware()` still read `Route::middleware()` (route-declared only). A controller that wires `auth:*` in its constructor or via `HasMiddleware` was authed in the document but treated as unauthenticated by the linter — so `operation.security-missing` silently did not fire when no scheme was derivable, and `publicendpoint.contradicts-middleware` missed the contradiction. Both readers now source the gathered list via `RouteMiddlewareGatherer::middlewareFor()` (injected into the two rules, string-filtered since the gathered list may contain closure middleware); the detection moved off the `OperationNode` value object (which can't reach the scoped gatherer) into `OperationSecurityMissing`. Route-declared middleware is unaffected — the gathered list is a superset.
- Class-form object casts (the modern `casts()` style) are now recognised, so the column is typed and its `@property` tag is no longer swallowed (#252). `Model::getCasts()` reports the caster FQCN for `['tags' => AsCollection::class]`, which `EloquentModelToSchema::castToProperty()` left unmatched — the column fell back to fully untyped (`{}`), losing both the conservative JSON-object default and (because `$casts` outranks the `@property` tag) any docblock precision such as `@property list<string> $tags`. The framework castables are now mapped before the keyword normalisation: `AsCollection` / `AsEncryptedCollection` / `AsArrayObject` / `AsEncryptedArrayObject` behave like the string-form JSON casts (inheriting #249's `@property` list disambiguation), and `AsStringable` → `string`. Parameterised forms (`AsCollection::of(Foo::class)` → `…AsCollection:Foo`) are handled by stripping at `:`. Separately, an **unrecognised** cast — a custom `CastsAttributes`, unknowable at Tier 0 — now defers to the `@property` tag before the untyped fallback at both call sites (`propertyFor()`, `schemaFor()`), the same precedence #249 established; a cast column is still always at least untyped. `AsEnumCollection` / `AsEnumArrayObject` (which carry an enum-class parameter) remain out of scope and take that `@property`-tag path. See [Auto-derivation → Property sources and precedence](docs/auto-derivation.md#property-sources-and-precedence).
- Multi-verb routes (`Route::match(['get', 'post'], …)`) now gate verb-conditional inference on the verb actually being emitted, not the route's first registered verb (#245). `PathsStage` built each operation once and fanned the same build out across every verb, while `ActionDescriptor::httpMethod` reported `methods[0]` — so on a `['get', 'post']` route the GET-only inferences (the `$request->*()` query-accessor scan, the GET/HEAD inline-`validate()` → query-parameter hand-off) leaked onto the POST twin, and the write-verb inferences (the inline-`validate()` request body) never fired on it; verb order flipped which way it broke. `ActionDescriptor` gains a per-operation verb (`withHttpMethod()`); `PathsStage` now builds each non-HEAD verb against that descriptor, so every consumer sees the emitted verb. Single-verb routes are unaffected — `Route::get` yields `[GET, HEAD]`, HEAD is skipped, so they build exactly once as before; only genuine multi-verb routes build per verb.
- The Tier-1 body-scan literal mapper now always emits an `items` schema for a `type: array` it can't constrain, so `openapi:generate`'s validation pass can't be crashed by an inline `response()->json([...])` / Resource `toArray()` / Fractal `transform()` body whose list elements are unreadable (#265). `SchemaDefinitionFromLiteral` returned a bare `{type: array}` (no `items`) for empty literals and heterogeneous / first-element-unreadable lists; swagger-php rejects an items-less array on both supported majors (`@OA\Items() is required …`). The downstream `SchemaFromArrayDefinition` guard (added in #235) already grafted an unconstrained `items: {}` on every consumer path, so the document was valid in practice — this hardens the source so the mapper produces a valid shape on its own, independent of any downstream repair, and adds the missing feature-level regression that runs the validation pass (the rest of the suite uses the non-validating `generateSpec()` helper). Final spec output is unchanged. The sibling field-attribute path was fixed the same way in #115.
- A wildcard validation key now forces its parent field to `type: array`, overriding a conflicting scalar rule on the same key (#271). A ruleset like `['a' => 'string', 'a.*.b' => 'integer']` emitted an incoherent `a: {type: string, items: {…}}` — a scalar type with `items` grafted on — because `ValidationRulesToSchema::nodeToDescriptor()` kept the parent's `string` type (`type ??= 'array'`) while still attaching the wildcard element. In Laravel `a.*` means `a` is a list, so the wildcard is authoritative about the shape; the parent now resolves to `a: {type: array, items: {type: object, properties: {b: {type: integer}}}}`. Non-conflicting dot/wildcard rulesets (the array parent never carries a scalar type rule) are unchanged. Pre-existing since the dotted/wildcard merge logic landed (#136); surfaced during the epic-#5 review because the inline-`validate()` reader (#9) adds a second, common route into this shape.
- `#[PublicEndpoint]` now suppresses the middleware-derived 401 (and scope-derived 403), so a declared-public operation no longer self-contradicts (#259). The attribute clears `security` (→ `security: []`, affirmatively public), but `MiddlewareErrorContributor` still emitted the implicit 401 from the route's auth middleware — the document then claimed an endpoint was public *and* documented a 401 Unauthenticated response. `security` is derived only from `auth:*` / `scope:*` / `scopes:*` middleware, so the contributor now consults the attribute (the same detection `OperationBuilder::resolveSecurity()` uses) and skips exactly those kinds for a declared-public operation. The `can`-derived 403 (a Laravel authorization gate, not part of `security`) and the `throttle`-derived 429 (rate limiting) are independent of authentication and stay. Fixes both the route-declared and controller-applied (constructor / `HasMiddleware`) middleware paths. See [Auto-derivation → Controller middleware](docs/auto-derivation.md#controller-middleware).
- Eloquent `array` / `json` / `collection` casts no longer document JSON **list** columns as `type: object` (#249). `castToProperty()` mapped the JSON casts uniformly to `object`, and because `$casts` outranks the `@property` tag, a precise docblock generic never got a say — Vito's `Site::$aliases` (`array` cast, `@property array<int, string>`, serializes as `["a.example.com", …]`) documented as an object in every consuming schema. For the ambiguous casts the reader now consults the column's `@property` tag (new `TypeNodeResolver::listValueType()` — no new parsing machinery): a list-shaped generic — `list<T>`, `array<int, T>`, or `T[]`, one level deep, leading nullable unwrapped — yields `{type: array}` with typed `items` when `T` is a scalar keyword (a non-scalar element yields a bare `array`); map-shaped generics (`array<string, T>`), single-argument `array<T>` (key type unknown), and untagged columns keep the conservative `object` default, and the `object` cast is always an object. Applies to direct model schemas and `propertyFor()` consumers (inferred Resource fields) alike. See [Auto-derivation → Property sources and precedence](docs/auto-derivation.md#property-sources-and-precedence).
- Query parameters are now deduplicated across resolvers by `name`+`in`, so two resolvers emitting the same parameter no longer produce a duplicate entry — which is invalid OpenAPI (a parameter is unique on name+location). This happens when, say, a Core `#[QueryParam('sort')]` and the QueryBuilder plugin's `#[AllowedSort]` both name `sort` on one action. `OperationBuilder` keys the collected query parameters by `name`+`in`; resolvers run in plugin order (Core first) and a **later resolver wins**, so a plugin's richer parameter replaces an earlier same-named one. The existing `parameter.duplicate-name` lint rule still surfaces the collision so it can be resolved intentionally. (#243)
- The `SwaggerPhp` harvester no longer silently merges an authored `@OA` operation **declared on a parent class or trait** onto the wrong place — or, more precisely, no longer silently *fails* to merge it (#187). `AuthoredAnnotationScanner` keys authored operations by the class that physically declares the annotation (swagger-php's `_context`), but the harvester looked them up by the **route's** controller; when the routed controller inherits the handler from an abstract base or a trait, the keys differed and the authored operation was dropped with no diagnostic. `operationForMethod()` now keeps the exact-match fast path and, only on a miss, walks the route controller's ancestry — parent classes and used traits (recursively) that declare the method — retrying the lookup against each. Trait-declared annotations are now indexed too (the scanner reads `_context->trait`, not just `_context->class`). Pure Tier-0 reflection. (#187)
- The `SwaggerPhp` harvester now surfaces an authored-schema **name collision** instead of dropping the authored definition silently (#186). An authored `@OA\Schema(schema="Invoice")` whose name matches a convention-derived component already registered under that key (e.g. a Spatie `Data` class or API Resource also named `Invoice`) is dropped — the shared `ComponentSchemaRegistry` is first-wins — so the authored operation's `$ref` resolves to the *convention* shape, not the one the author wrote. The harvester now keeps that first-wins behaviour (the convention component, registered earlier in the pipeline, wins) but reports the collision: a generation-time warning plus a new `component.schema-name-collision` lint finding (level 1, registered by the off-by-default `SwaggerPhp` plugin) carrying the colliding name and authored source class, so a class-scoped `#[IgnoreLint]` can match. Rename the authored schema, or remove it once inference covers it. An identical re-registration of the same schema object (transitive dedup) is not treated as a collision. See [Linting](docs/linting.md). (#186)
- Two controllers sharing a short name in different namespaces no longer collide on a single method-level `#[RequestField]` request-body component (#224). `RequestFieldRequestSchemaResolver::componentKey()` keyed the synthetic component as `{ControllerShortName}{Method}Request` and registered it via the first-wins `ComponentSchemaRegistry::registerNamed()`, so e.g. `Admin\CartController::storeCoupon` and `Shop\CartController::storeCoupon` produced the same key — the second controller's schema was silently dropped and its operation `$ref`'d the first's, advertising the wrong body when their fields diverged. The key is now derived from a namespace-qualified synthetic name routed through `ComponentSchemaRegistry::reserveKey()`, which disambiguates with a namespace segment on collision (`CartControllerStoreCouponRequest` vs `ShopCartControllerStoreCouponRequest`); non-colliding keys stay byte-stable since the bare basename is preferred. Mirrors the disambiguation the `$ref`-pooled Data/Resource/FormRequest schemas already get. Found during the #219 re-review. (#224)
- Per-spec `info` overrides now deep-merge into the root `info` instead of clobbering nested groups. `SpecRegistry::buildSpec()` merged the per-spec `info` override with a shallow `array_merge`, so overriding a single nested field (e.g. `info.contact.email`) wiped its siblings (`info.contact.name`) and any unrelated nested group (`info.license`) — leaving an incomplete `info` block in that spec's document. The merge is now `array_replace_recursive`, scoped to `info` only; `servers`/`tags` remain wholesale replacements by design. (#47)
- An unmapped object type no longer leaks the host app's fully-qualified class name into a schema description. `JsonSchemaFromType::fromObjectType()`'s fallback branch — reached when a property's class resolves to neither a registered component schema nor a known shape (date/uuid/url-routable) — emitted `Unmapped object type: App\Models\Internal\SecretThing` verbatim into the consumer-facing spec, exposing internal namespace structure. The class is now rendered as a human-readable resource name (`Secret Thing`) via a new shared `Radiergummi\OpenApi\class_resource_name()` helper (`Str::headline(class_basename(…))`), consistent with the existing `class_basename`-only model-binding fix (#163). The same helper is applied to the unit-enum description (`Values of unit enum Group Membership …`) and the route-model-binding description (`Bound by id of Group Membership.`), so multi-word class names now read as words; the FQCN still appears only in the developer-facing generation log, never the spec. in a hybrid Passport + Sanctum app (#104). Since #33 a `auth:sanctum` + `abilities:read,write` route emits `['sanctum' => ['read','write']]`, but both rules validated *every* requirement's scopes against the Passport scope registry (`Passport::scopes()`) regardless of the requirement's scheme **type** — so the Sanctum abilities `read`/`write` were flagged as undefined Passport scopes. Scopes only have a document-level registry for `oauth2`/`openIdConnect` schemes; `http`/`apiKey`/`mutualTLS` schemes (the Sanctum bearer scheme, custom bearer/api-key schemes) carry no scope catalogue. Both rules now resolve a requirement's scheme `type` from `components.securitySchemes` (new shared `Lint\SecuritySchemeTypes` helper) and skip scope validation for non-scope-bearing schemes; the Passport `oauth2` path is unchanged, and an undeclared scheme is still validated (left to `security.scheme-undefined`). Surfaced by the #63 review of #33. (#104)
- Properties typed against the `DateTimeInterface` interface now map to `string` / `format: date-time` (#148). `JsonSchemaFromType::fromObjectType()` matched only the four concrete date classes (`DateTime`, `DateTimeImmutable`, `Carbon`, `CarbonImmutable`) — `is_a('DateTimeInterface', DateTime::class, true)` is `false`, since the interface is the supertype — so a property typed against the idiomatic, recommended interface (Spatie's `DateTimeInterfaceCast` returns it; the `examples/spatie-data` Data classes use it) fell through to the generic `Unmapped object type: DateTimeInterface` branch and emitted a bare `type: string`. The four checks collapse to a single `is_a($className, DateTimeInterface::class, allow_string: true)`, which covers all four concretes and the interface. Consequence: a `DateTimeInterface` field additionally validated with `#[Date]` now reports `format: date-time` (type-accurate — the value carries time) rather than the validation-derived `format: date`; the `examples/spatie-data` and `examples/combined` snapshots are regenerated accordingly.
- `openapi:lint`'s `response.description-missing` (level 0) no longer false-fires on the generator's own auto-derived error responses (#129). Shared error responses (`401`/`422`/`429`, …) are emitted as Reference Objects (`$ref: '#/components/responses/Unauthorized'`) whose description lives on the referenced component — valid OAS 3.1 — but the lint tree builder read `description` straight off the un-dereferenced response node, where it is absent, so the rule fired on every Sanctum-protected route and every `FormRequest`-validated write (28 of 34 findings on one surveyed app's `/api`). `SpecTreeBuilder` now indexes `components.responses` and dereferences a `$ref` response to the referenced component's description; a dangling `$ref` leaves the description absent (that is `ref.broken`'s job) rather than crashing or silently passing. The same latent shape for `$ref`'d headers/parameters is noted in code but not reachable today — the generator only ever inlines headers and parameters, never `$ref`s them. Surfaced by the Vito and AdvisingApp full-spec attribute proofs. (#129)
- A `#[Response(schema: [...])]` literal with a nested `properties` (object) or `items` (array) now validates on swagger-php 5.x (#116). `buildResponseFromAttribute()` passed the raw array straight to `new OA\Schema(...)`, leaving the nested arrays unconverted; swagger-php 5.x's validator rejects that (`@OA\Schema()->properties is an object literal`), failing `openapi:generate` — while 6.x silently tolerated it. The literal is now recursively converted into an `OA\Property` / `OA\Items` object graph, which validates on both the `^5.8` and `^6.1.2` lines. Surfaced by the Vito full-spec attribute proof. (#116)
- `openapi:generate` no longer hard-fails when a field attribute declares `type: 'array'` (#115). An items-less array schema is invalid and swagger-php rejected it, aborting the whole run — so a single `#[ResourceField('tags', type: 'array')]` took down generation. Array schemas now always carry an `items` schema. The field attributes (`#[ResourceField]`, `#[RequestField]`, `#[ResponseField]`, `#[QueryParam]`) gain an `items:` parameter naming the element type (`items: 'string'` → `items: {type: string}`); when omitted, an array emits a permissive `items: {}`. Surfaced by the Vito full-spec attribute proof. (#115)
- `openapi:generate` no longer aborts when a host app's `FormRequest::rules()` or Spatie Data `getValidationRules()` raises an `Error`/`TypeError` (rather than an `Exception`) at spec time — e.g. a `rules()` body that passes a route-binding placeholder into a typed Rule constructor (`TypeError`), calls a method on a null `auth()->user()` (`Error`), or reads an uninitialised typed request property. Both seams catch `Throwable` again — they invoke arbitrary host-app code, unlike the library-internal resolvers the `Exception`-only `ResolverFaultBoundary` guards — degrading to a placeholder schema plus a `request-body.schema-degraded` finding. Regression surfaced re-running the OSS-survey dogfooding (Invoice Ninja, Bagisto, Pelican, Koel).
- `openapi:lint --path` / `--diff` no longer leak generation-time findings for out-of-scope routes (#50). The post-generation filter kept any finding with no `routeUri`, treating it as route-agnostic — but several extractor findings are *schema*-derived (`rule.unknown`, `rule.invalid-enum-value`, `request-body.schema-degraded`), emitted from registry-cached builders that have no single route because a FormRequest / Data class is `$ref`'d by many routes. These now carry their `source_class` and are scoped by *reachability*: a schema finding survives the filter exactly when an in-scope route references that schema (so a schema shared between an in-scope and an out-of-scope route stays visible — the filter never hides an in-scope finding). `errors.resolver-failed`, which is genuinely route-scoped via its `ErrorDescriptor`, now stamps `routeUri` directly. These recorded the originating class under an ad-hoc `source_class` context key that `SuppressionDirective::classMatches()` never read; they now use the canonical `Finding::CONTEXT_SOURCE_CLASS` key like every other source-class-bearing finding, so class-scoped suppression reaches them.
- Named routes with characters outside the codegen-safe identifier set no longer leak an invalid `operationId` that the bundled linter then rejects (#42). `PathsStage::buildOperationId()` previously returned the route name verbatim, so a namespaced name like `api:client.show` (the `:`) or a name carrying a bound segment (the `{}`) tripped the package's own `operation.id-invalid-chars` rule on a fresh run. It already degraded gracefully for a missing controller *class*; it now applies the same `hasMethod()` guard for a missing *method*, emitting an `ActionDescriptor` with a null method rather than letting a `ReflectionException` escape. Surfaced by OSS-survey dogfooding against BookStack (`docs/internal/dogfooding/2026-05-30-bookstack-route-introspector-missing-method-crash.md`).
- Closure (and other non-string) route middleware no longer crashes generation. Routes may carry inline closure middleware via controller middleware, which `gatherMiddleware()` surfaces without casting to string. `SecurityExtractor::expandGroups()` (`Cannot access offset of type Closure in isset or empty`) and the `MiddlewareErrorContributor` string-typed detectors (`Argument #1 ($entry) must be of type string, Closure given`) both assumed `list<string>`; they now skip non-string entries, which can neither name a middleware group nor map to a security scheme. Surfaced by OSS-survey dogfooding against BookStack (`docs/internal/dogfooding/2026-05-30-bookstack-security-extractor-closure-middleware-crash.md`).
- `SchemaFromFormRequest` no longer crashes when `rules()` reads runtime request state. The FormRequest is instantiated with a permissive route + user context: `$this->route('foo')` resolves to a stub for any binding name, `$this->user()` resolves to the same stub, and chained property/method access on the stub terminates without throwing. The rules array's structure (keys, types, required-ness, file detection) is preserved; only the values inside `Rule::in([...])` etc. are opaque placeholders — which is correct, since those values are not part of the OpenAPI schema. The existing `request-body.schema-degraded` finding now fires only for the residual cases (rules() branching on a type check, calls into a container service that is not bound at spec-time). The fix-hint points consumers at `#[IgnoreLint('request-body.schema-degraded', reason: '…')]` and `docs/request-bodies.md` documents the limitation. Surfaced by P4 dogfooding (`docs/internal/dogfooding/2026-05-29-p4-formrequest-rules-runtime-state-crashes-introspection.md`).
- Class-level `#[IgnoreLint]` on a request payload class now suppresses findings on the properties of the component schema that class produces. Previously the directive was collected but never matched — the `ClassScope` branch of `SuppressionDirective::suppresses()` only compared source file paths, while findings emitted from the spec tree carry a JSON-pointer location (`#/components/schemas/<key>/properties/<field>`) and no source file. The walker now stamps `CONTEXT_SOURCE_CLASS` and `CONTEXT_SOURCE_MEMBER` on every finding emitted under a `ComponentSchemaNode` whose owning class is known, and the directive matches structurally on that class context in addition to the existing file-path match. The class-to-component-key map is exposed on `ComponentSchemaRegistry::componentClassMap()`. Surfaced by P1 dogfooding (`docs/internal/dogfooding/2026-05-29-p1-class-level-ignorelint-not-honored-for-component-schemas.md`).
- `Illuminate\Foundation\Http\FormRequest` is now registered as a payload class by `CorePlugin`, so a class-level `#[IgnoreLint]` on a FormRequest is collected when the FormRequest appears as a controller-method parameter. Previously the directive was silently dropped because `SuppressionCollector::fromDataParameter` only descended into types matching a registered payload class, and `FormRequest` was not in the list. `Illuminate\Http\Resources\Json\JsonResource` is now likewise registered by `ApiResourcesPlugin`. A new `SuppressionCollector::collectFromComponentSchemas()` method walks `ComponentSchemaRegistry::componentClassMap()` after generation, picking up class-level directives on classes (typically return-typed `JsonResource`s) the descriptor walk never reached. Surfaced by P4 dogfooding (`docs/internal/dogfooding/2026-05-29-p4-formrequest-rules-runtime-state-crashes-introspection.md`).
- `@throws` on a trait-composed controller method is now resolved against the *trait's* file context (its namespace and `use` imports), not the using class's. PHP's `ReflectionMethod::getDeclaringClass()` reports the using class for a method composed via `use TraitName`, which would make phpDocumentor's `ContextFactory` read the using class's imports and miss any `use` statements that only live in the trait's file — so a bare `@throws SomeAppException` in a trait silently resolved to the wrong FQCN and the per-class `#[ExceptionResponse]` attribute path was unusable for trait-bound controller methods. `ThrowsExtractor::contextFor()` now walks `getTraits()` depth-first to find the trait that lexically declares the method and substitutes its `ReflectionClass` before invoking `ContextFactory::createFromReflector`. Direct methods, inherited methods, and `ReflectionFunction` reflectors are unaffected. Surfaced by P2 dogfooding (`docs/internal/dogfooding/2026-05-29-p2-throws-extractor-trait-context.md`).
- Path parameters now always emit `required: true`, as required by OpenAPI 3.x §4.8.12.1 ("If the parameter location is `path`, this property is REQUIRED and its value MUST be `true`"). Previously, Laravel's `{param?}` optional-segment syntax produced `required: false`, which yields a spec-invalid document and is rejected by downstream tooling (Stoplight, Spectral, Scalar, openapi-generator). The optional-in-URL signal is preserved as a description suffix ("Optional in URL — the segment may be omitted when calling this route.") so it isn't silently lost. Surfaced by P1 dogfooding (`docs/internal/dogfooding/2026-05-29-p1-optional-path-param-emits-invalid-spec.md`).
- Stock Laravel `Illuminate\Validation\Rules\{Email, Exists, Unique, NotIn}` rule objects are now mapped to JSON Schema constraints in `ValidationRulesToSchema::applyObjectRule()`. `Email` becomes `type: string, format: email` (with an "MX record will be validated." description note when `validateMxRecord()` is set); `Exists` and `Unique` contribute database-constraint descriptions referencing the table/column; `NotIn` contributes a description listing the disallowed values. Previously these factory rules emitted `rule.unknown` findings and their constraints were silently dropped. `ImageFile` is unchanged — it extends `File` and is already handled by the existing `File` branch. Surfaced by P1 dogfooding (`docs/internal/dogfooding/2026-05-29-p1-stock-laravel-rule-classes-unhandled.md`).
- Laravel wildcard rule keys (`*` and `foo.*`) no longer emit a literal property named `*` or silently drop the constraints. A bare `*` rule key — Laravel's idiom for "validate every value in the request body" — now produces a JSON Schema `additionalProperties` entry with the wildcard's constraints applied, instead of a misshapen `properties: { "*": …}` schema. A `foo.*` rule key without a separately-declared `foo` parent now synthesises the parent as `type: array` with the wildcard rule's constraints landing on `items` (previously the wildcard's `itemsFields` entry was silently dropped because no matching property had been created). Deeper-nested paths like `foo.bar.*` and `foo.*.bar` remain unmodelled for now and continue to fall under the existing "some nested fields were skipped" schema description. Surfaced by P1 dogfooding (`docs/internal/dogfooding/2026-05-29-p1-wildcard-rule-key-emits-asterisk-property.md`).

- `IdentifierCase` gained a `fromConfig()` static factory mirroring
  `VisibilityMode::fromConfig()`; `AbstractNamingRule` uses it instead of
  inlining the enum coercion, and the cached `$pattern` property is gone —
  `$case->pattern()` is a pure `match`, so the caching was buying nothing.
- `VisibilityAttributeNoOp` now takes a `VisibilityResolver` and reads
  `defaultMode()` from it instead of re-running `config('openapi.visibility.default')`
  through `VisibilityMode::fromConfig()` on every route check.
- `SchemaFromFormRequest` now takes a `Psr\Log\LoggerInterface` constructor
  argument instead of reaching for `Illuminate\Support\Facades\Log`, matching
  the sibling pipeline classes (`PaginatorResponseResolver`,
  `SchemaFromDataClass`). The warning message changed from
  "[OpenAPI] Schema introspection failed for FormRequest …" to
  "SchemaFromFormRequest failed for …" for consistency with the sibling
  classes.
- `GenerateCommand`, `ClearCommand`, and `WhyCommand` now use the
  `#[Signature]` / `#[Description]` attribute pair (already used by
  `LintCommand`) instead of the `$name` / `$description` properties plus
  `configure()`. Argument and option names continue to be exposed as
  `ARGUMENT_*` / `OPTION_*` constants on each command class.
- `examples/generate.php` now passes the output path via `--output` (the
  documented option name). The previous `path` positional was rejected by
  Symfony's argument parser after the `path` arg was renamed to `spec` in
  the multi-spec refactor.
- `docs/config.md` lists `output_path` under the top-level keys table.
- `docs/attributes.md` lists `#[Spec]` in the operation-level catalog with a
  pointer to `docs/multi-spec.md`.
- `config/openapi.php` no longer references the internal "Plan A2" identifier
  next to the `lint.baseline` placeholder.
- `#[Header]` constructor shape now mirrors `#[ResponseHeader]` (minus `status`). New
  optional arguments: `format` (passed through to the schema) and `deprecated` (passed
  through to the parameter). Argument order is now `name, description, type, format,
  example, required, deprecated` — the previous order was `name, description, required,
  type, example`. Existing call sites use named arguments and are unaffected.
- Route exclusion now lives entirely in `InclusionEvaluator`. `RouteIntrospector` no longer
  takes a filter list and unconditionally yields every Laravel route; vendor-route skippers
  (Telescope/Nova/Ignition/Passport) and any `config('openapi.filters')` entries are applied
  at the evaluator stage. Consequence: every exclusion — including vendor routes — now
  produces a `RouteSkipped` event, a `trace` entry visible to `openapi:why`, and a
  `SkipReason::GlobalFilter` on the decision. The lint pipeline pre-filters descriptors via
  the new `InclusionEvaluator::passesGlobalFilters()` to keep vendor routes out of pre-build
  rules and the tree walk.
- **`spatie/laravel-data` is now a soft dependency.** Moved from `require` to
  `require-dev`; the `SpatieDataPlugin::register()` body is guarded by
  `class_exists(\Spatie\LaravelData\Data::class)` and silently no-ops when the package
  is absent. `OpenApiServiceProvider::registerSpatieDataPlugin()` is guarded similarly,
  while the Core FormRequest bindings (`PayloadParameterScanner`,
  `SchemaFromFormRequest`, `FormRequestRequestSchemaResolver`, `RequestBodyExtractor`,
  `StandardResponsesExtractor`, `ExampleFileLoader`) moved out of that method into a new
  `registerRequestSchemas()` so they survive without Spatie installed. Consumers using
  Spatie Data: `composer require spatie/laravel-data` and everything works as before.
- `LintCommand` shrank from ~700 LOC to ~150 LOC. The body of `handle()` now parses CLI
  options into a `LintOptions`, hands off to `LintRunner`, and renders the resulting
  `LintResult` through the chosen `Formatter`. No behaviour change.
- `--diff` no longer hardcodes `develop` as the upstream branch. The default ref is now
  derived from git itself: `git symbolic-ref refs/remotes/origin/HEAD` first, then the
  first existing local branch among `main`, `master`, `trunk`, then `HEAD~1`. The
  `--diff infra-touched` detection also drops the host-project-specific paths
  (`app/Support/OpenApi/`, `app/Providers/OpenApiServiceProvider.php`) — only the
  published OpenAPI config (`config/openapi.php`) triggers the full-route-set fallback.
- `config/openapi.php` defaults tightened: `info.version` is now
  `env('API_VERSION', '1.0.0')` instead of the hardcoded `'0.1.0'` (consumers who
  publish the config no longer ship `0.1.0` by accident), and `lint.baseline` is now
  `null` instead of `base_path('openapi-baseline.json')` (the existing comment already
  documented this as the disable sentinel; the default is now aligned).
- Removed `reset()` methods on the scoped pipeline classes — they were redundant under
  the `scoped` container lifecycle (each scope yields a fresh instance) and the
  docblock on `OpenApiServiceProvider` already acknowledged this. Affected classes:
  `OpenApiGenerator`, `OperationBuilder`, `ComponentSchemaRegistry`, `ExampleFileLoader`,
  `ThrowsExtractor`, `RouteIntrospector`. The lint-rule `Resettable` interface is
  unaffected — `SpecTreeWalker` still calls `Rule::reset()` before each walk. Callers
  that need a fresh pipeline mid-scope should call `$app->forgetScopedInstances()`
  (one existing test was migrated to demonstrate the pattern).
- Internal refactor of `OpenApiGenerator`: document assembly now runs through a
  `SpecPipeline` composed of typed stages (`RootStage`, `PathsStage`,
  `ComponentsStage`, `SecurityStage`, `TransformersStage`). No behaviour
  change. `OpenApiExtensions` (static-callable transformer surface) is
  unchanged.

### Added
- `#[Expose]` attribute (`src/Core/Attributes/Expose.php`) — opt routes into the
  generated document when the new hidden-default mode is active. Mirrors
  `#[Hide]` with the same mutually-exclusive `only` / `except` environment
  scoping. `#[Hide]` always wins on conflict.
- `visibility.default` config flag (`config/openapi.php`) — accepts `'public'`
  (the current behaviour) or `'hidden'` (every route excluded unless `#[Expose]`
  applies).
- `visibility.hide-expose-conflict` lint rule (level 1) — reports routes whose
  `#[Hide]` and `#[Expose]` env scopes overlap in the current environment.
- `visibility.attribute-no-op` lint rule (level 2) — reports unconditional
  visibility attributes that have no effect under the active default mode.

- `Radiergummi\OpenApi\Plugins\Fractal\Serializer` enum (cases `DataArray`,
  `ArraySerializer`, `JsonApi`) plus a `serializer:` parameter on
  `#[FractalResponse]` — names the Fractal serializer the endpoint runs at
  runtime so the generated envelope matches it. `FractalEnvelopeFactory` now
  dispatches per serializer: ArraySerializer single is a bare `$ref` (no
  envelope), collection is a top-level array; JsonApi produces resource
  objects `{data: {type, id, attributes: $ref}}` under
  `application/vnd.api+json` with hyphenated `meta.pagination` keys when
  paginated. The default `Serializer::DataArray` is unchanged. Custom
  serializers outside this set still use `#[Response]` to override. (OAPI-052)

- `fractal.transformer-class-missing` lint rule (level 1, registered by
  `FractalPlugin`) — flags `#[FractalResponse]` attributes that name a
  transformer class that does not exist (typos like `BookTrnasformer::class`).
  Surfaces during `openapi:lint` what would otherwise only appear in the
  generation log when `FractalResponseResolver` silently drops the operation's
  response. (OAPI-059)
- `SchemaDescriptor::toSchema(string $defaultType = 'string')` — canonical
  helper that builds a standalone `OA\Schema` from a descriptor and applies the
  OAS 3.1 `type: [..., 'null']` widening (which `toOpenApi()` deliberately
  omits). Used by `CoreQueryParameterResolver` and
  `QueryBuilderParameterResolver`, replacing the duplicated 4-line snippet they
  carried. (OAPI-049)
- Feature test (`DefaultPluginsConfigTest`) asserts the shipped default
  `config/openapi.php` `plugins` array generates a clean document — a typo in
  either commented-out FQCN or an accidental uncomment would now fail in CI.
  (OAPI-057)
- `openapi.security_schemes` config map — registers OpenAPI security schemes by name. Each entry
  is passed through to swagger-php's `OA\SecurityScheme`; the map key becomes `securityScheme`.
  Entries are merged with the Passport-derived `oauth2` / `oauth2ClientCredentials` pair (emitted
  only when Passport is installed and its named routes are registered); config entries win on
  key collision. `#[Security]` now accepts an optional `scheme:` parameter naming which
  configured scheme the requirement targets — existing `#[Security(['scope'])]` usages keep
  working against the project default scheme. (OAPI-042)
- `#[ResponseHeader]` authoring attribute — repeatable on methods/functions, declares a header
  on the response whose `status:` it targets (defaults to 200). Carries `name`, `description`,
  `type`, `format`, `example`, `required`, `deprecated`. Replaces the request-`#[Header]`
  workaround for documenting headers like `Location` on 201 responses. (OAPI-041)
- `DataResponseResolver` (SpatieData plugin) — auto-derives the primary `200 OK` response from a
  Spatie `Data` return type, a `DataCollection<int, Item>` (item class read from the `@return`
  PHPDoc generic), or a `PaginatedDataCollection` / `CursorPaginatedDataCollection` (renders the
  matching paginator envelope). Mirrors the ApiResources plugin's `ResourceResponseResolver`.
  Explicit `#[Response]` attributes still take precedence. (OAPI-040)
- `CoreQueryParameterResolver` — reflects `#[QueryParam]` attributes off controller methods (and
  classes, for shared parameters declared once) and emits OpenAPI query-parameter entries with
  the attribute's full `FieldAttribute` surface (type, format, enum, default, nullable, bounds).
  Closes the documentation-vs-implementation gap where `#[QueryParam]` existed but was never
  read. (OAPI-039)
- `#[Deprecated]` authoring attribute (in `Radiergummi\OpenApi\Attributes`) — symmetric to
  the PHPDoc `@deprecated` tag and the PHP 8.4 native `#[\Deprecated]` attribute. Targets
  methods, functions, properties, promoted constructor parameters, and class constants. Sets
  `deprecated: true` on the generated operation (method-level) or schema property
  (property / parameter level). (OAPI-043)
- `SkipPassportRoutes` route filter registered by default — Laravel Passport's CRUD endpoints
  (route names under the `passport.*` prefix) are filtered out of generated specs alongside
  Nova / Telescope / Ignition. The filter tolerates Passport being absent. (OAPI-044)
- `examples/` suite: five runnable flavors (vanilla, form-requests, spatie-data, query-builder, combined)
  that all expose the same flights+bookings API and ship a generated `openapi.yaml` snapshot.
  Verified in CI against fresh generation, OpenAPI 3.1 validity, and `openapi:lint`.
- Laravel paginator return types (`LengthAwarePaginator`, `Paginator`, `CursorPaginator`) are
  now documented automatically. The paginated item type is resolved from a `#[ResponseResource]`
  attribute or a `@return Paginator<Item>` PHPDoc generic.
- Eloquent API Resources (`JsonResource` / `ResourceCollection`) are now
  documented automatically via the default-enabled `ApiResourcesPlugin`. Each
  resource declares its output keys with repeatable class-level
  `#[ResourceField]` attributes; single responses emit the `{data}` envelope and
  collections the `{data, links, meta}` envelope. Three lint rules
  (`resource.fields-undeclared`, `resource.field-type-missing`,
  `resource.response-ambiguous`) report incomplete declarations.
- `spatie/laravel-query-builder` filter/sort/include query parameters are now
  documented via the optional `QueryBuilderPlugin` (shipped disabled — uncomment
  it in `config/openapi.php` after installing the package). Endpoints declare
  parameters with `#[AllowedFilter]`, `#[AllowedSort]`, and `#[AllowedInclude]`.
  Two lint rules (`query-builder.params-undeclared`,
  `query-builder.filter-type-missing`) report incomplete declarations.
- `league/fractal` transformer responses are now documented via the optional
  `FractalPlugin` (shipped disabled — uncomment it in `config/openapi.php` after
  installing the package). Transformers declare output keys with
  `#[TransformerField]` and includes with `#[TransformerInclude]`; endpoints bind
  to a transformer with `#[FractalResponse]`, which accepts `collection: true`
  for a flat collection and `paginated: true` for a paginated one (envelope
  includes `meta.pagination` matching Fractal's `IlluminatePaginatorAdapter`).
  Four lint rules (`fractal.response-unbound`, `fractal.fields-undeclared`,
  `fractal.include-transformer-missing`, `fractal.duplicate-key`) report
  incomplete or invalid declarations.
- `openapi.security_default_scheme` config option — names the scheme that
  `#[Security(['scope'])]` (without `scheme:`) and middleware-derived
  `forRoute()` security target by default. Accepts a string (single scheme) or
  a list of strings (multiple OR-alternatives). When unset, resolution falls
  back to Passport's `oauth2` + `oauth2ClientCredentials` pair if installed,
  otherwise the first scheme declared in `openapi.security_schemes`, otherwise
  an empty requirement — preserving the previous behaviour for projects that
  do not opt in. Mixed-scheme projects (Passport + custom bearer) can now set
  this once instead of passing `scheme:` on every `#[Security]`. (OAPI-045)
- `Radiergummi\OpenApi\Core\Lint\ReflectionAttributeCache` — per-walk cache
  attached to `LintContext` that wraps `getAttributes()` bucketing and
  `ReflectionClass` construction. Sibling lint rules that introspect the same
  target class (resource, transformer) or the same operation method now share
  the cache. Resource, Fractal, and QueryBuilder lint rules migrated to use it
  (and to read controller / method attributes through the new
  `ActionDescriptor::actionAttributes()` helpers instead of allocating fresh
  `ReflectionClass` / `getAttributes()` walks per rule). (OAPI-054)

### Changed (breaking)
- `#[Hide]` constructor argument renamed: `environments` → `only`. Also gains
  `except` as an exclusive alternative. Migration: rewrite
  `#[Hide(environments: [...])]` to `#[Hide(only: [...])]`.

### Changed
- `SpecTreeBuilder` now resolves `allOf`-composed schema properties when
  building `FieldNode` trees. A schema written as
  `allOf: [{$ref: Base}, {properties: {…}}]` exposes both the
  `$ref`-inherited properties and the local ones in
  `ComponentSchemaNode->fields`, with a cycle guard against recursive `allOf`
  chains; the `required` list is unioned across branches. `oneOf` / `anyOf`
  are deliberately not composed. False positives in
  `schema.required-without-property` and false negatives in
  `schema.enum-type-mismatch` / every other `FieldRule` are now closed for
  `allOf`-composed schemas. (OAPI-038)
- `SecurityExtractor` and `ReturnTypeExtractor` now memoise per-run state on
  the instance: Passport availability (`class_exists` + 3× `Router::has()`),
  the router's middleware-groups snapshot, the parsed
  `openapi.security_schemes` catalogue, and per-reflector
  `genericArgument()` results. Both are bound as scoped singletons so the
  caches reset between requests under Octane. The biggest win is the
  `DocBlockFactory::create()` parse, which is now done once per method
  across all primary-response resolvers that consult the same `@return`
  generic. (OAPI-051)
- `ActionDescriptor` now exposes `controllerAttributes()` /
  `actionAttributes()` helpers that read each reflector's attribute list once
  per descriptor and bucket by attribute FQCN. `OperationBuilder` switched
  every `getAttributes(SomeAttribute::class)` call onto these helpers, so a
  build over `n` routes does `O(2·n)` attribute walks instead of `O(17·n)`.
  No behaviour change; the bucket cache is scoped to the descriptor's lifetime,
  so it carries no Octane-state risk. (OAPI-050)
- `#[ResponseHeader]` now also targets `TARGET_CLASS` and is read off both the
  controller and the action reflector by `OperationBuilder` — shared response
  headers (`X-Request-Id`, `X-RateLimit-Remaining`) can be declared once on the
  controller instead of repeated on every method. Method-level declarations win
  on `(status, name)` collision; declaration order is otherwise preserved. The
  shape now mirrors `#[Header]`. (OAPI-046)
- `SkipPassportRoutes` now exposes a parameterless `fromConfig()` factory and
  is registered through it in `OpenApiServiceProvider`, matching the shape of
  the sibling filters (`SkipNovaRoutes` / `SkipTelescopeRoutes` /
  `SkipIgnitionRoutes`). Behaviour is unchanged — Passport's route-name prefix
  is not user-configurable, so the constructor still takes no parameters; a
  class-level docblock spells that out so the deviation no longer reads as an
  oversight. (OAPI-047)
- `fractal.response-unbound` lint rule moved from level 1 to level 2 (opt-in),
  matching its `query-builder.params-undeclared` sibling. The rule's
  `description()` now spells out the blind spot (`fractal()` helper /
  `Spatie\Fractalistic\Fractal` facade are not detected) so the caveat surfaces
  in `openapi:lint --list-rules` output. Default-level lint runs no longer
  produce a silent zero-findings result that could be mistaken for endorsement
  in Fractal-heavy codebases. (OAPI-060)
- `PaginatorKind::fromClass()` now recognises Spatie's `PaginatedDataCollection`
  and `CursorPaginatedDataCollection` (FQCN-matched to keep Core free of plugin
  imports). `PaginatorResponseResolver` now claims those return types via the
  shared `RefSchemaResolver` chain (with `DataRefSchemaResolver` already in it),
  so `DataResponseResolver` shrank to single `Data` + non-paginating
  `DataCollection<…, Item>`. Paginator-envelope construction now lives in one
  place. (OAPI-048)
- `SchemaFromResource` now takes `Closure(): list<RefSchemaResolver>` to mirror
  the sibling `SchemaFromTransformer`; both sides of the cross-plugin
  construction graph are lazy, closing the latent OOM tripwire for a future
  third `SchemaFromX` + `XRefSchemaResolver` pair. (OAPI-055)
- `FractalResponseResolver`, `ResourceResponseResolver`, and
  `DataResponseResolver` now catch only `ReflectionException` — the documented
  tolerable failure mode. Real bugs (`TypeError`, schema-build logic errors,
  `Error` subclasses) now propagate so they surface in dev rather than
  disappearing into a warning log. (OAPI-058)
- Plugin-suite integration test (`PluginSuiteIntegrationTest`) tightened with
  negative assertions (paginator route is not Fractal-wrapped; resource and
  Fractal routes carry no QueryBuilder params), full Fractal envelope-shape
  coverage (single / collection / paginated), `#[AllowedInclude]` coverage on
  the paginator route, and an included transformer asserted to land as its own
  component schema. (OAPI-056)
- `composer.json` `require-dev` constraint for `league/fractal` loosened from
  `^0.20.2` to `~0.20.2` — explicit about allowing 0.20.x patch updates without
  claiming 0.21 forward compatibility. (OAPI-061)
- `config/openapi.php` Fractal-plugin comment now names both triggers
  (`league/fractal` and `spatie/laravel-fractal`) so users coming in via the
  Spatie wrapper have a signal that they already meet the requirement. (OAPI-062)
- PHPStan now runs at level 8 with `treatPhpDocTypesAsCertain` disabled and is a blocking CI check.
- Document generation now skips routes whose controller class cannot be resolved at introspection time, instead of aborting the entire run with a `ReflectionException`.
- Upgraded core dependencies to current major versions: `zircote/swagger-php` 6, `symfony/type-info` 8, and `phpdocumentor/reflection-docblock` 6.
- `league/fractal`, `spatie/laravel-fractal`, and `spatie/laravel-query-builder`
  are now listed under `suggest` — install the relevant package and uncomment
  the matching plugin in `config/openapi.php` to enable it.

### Fixed
- The `schema.constraints-missing` lint rule now handles OpenAPI 3.1 nullable type arrays (`type: [string, null]`). Previously such schemas caused a `TypeError` and were silently left unchecked.
- The lint spec-tree builder no longer fails when a media type's schema is a plain `$ref` string rather than an inline schema object; such schemas are now handled gracefully.
- Generated documents keep the OpenAPI 3.1 nullable form (`type: ['…', 'null']`). swagger-php 6 defaults its serialisation context to OpenAPI 3.0, which down-converts nullable unions to the removed `nullable` keyword; generation now pins a 3.1 context.
- `#[AllowedFilter(nullable: true)]` now widens the generated `filter[…]` schema to `type: ['…', 'null']`. Previously the `nullable` flag was accepted on the attribute but silently dropped from the wire schema.
